# FlashSync — тези до слайдів (≤ 5 хв)

Захист 16.11.2026. 7 слайдів, ~40 с на слайд. Цифри — з `results/eval/Test_3min_Take_001/`
(8 камер, 3.5 хв, 206 спалахів; модель на першій половині, перевірка на другій).

---

## 1. Motivation (30 с)

- Мокап-студія: 8 камер Xiaomi Yi, 1080p50, запис через Mocap Director → Captury.
- Немає genlock: камери стартують по черзі (крок ~0.46 с), годинники дрейфують, карта захоплення інколи дублює кадр.
- Тріангуляція потребує, щоб 8 кадрів були **одного моменту**. Розсинхрон 20 мс = 10 см руху кисті при 5 м/с.
- **Візуал:** кадр «BEFORE» з демо — той самий номер кадру, а камери показують різні моменти (розкид 2.3 с).

## 2. Introduction (35 с)

- Варіанти: апаратний genlock (дорого, ці камери не вміють), аудіо (луна, шум, точність ~кадр),
  таймкод, хлопушка в кіно (один момент, без дрейфу).
- Наш підхід: ESP32 блимає LED раз на секунду + лог `esp32_flashes.txt` з часом кожного спалаху →
  **ground truth** і для синхронізації, і для чесної оцінки.

## 3. Description — пайплайн (60 с)

1. **Пошук LED** — epoch folding: усереднення відео з періодом спалаху → карта мерехтіння → MAD-поріг →
   морфологія → connected components → перевірка періодичності. 16 / 16 LED на 6 камерах, рух актора не заважає.
2. **Спалахи** — ковзний фон (30-й перцентиль), поріг Otsu / 6σ, об'єднання LED, детекція повторів кадрів.
3. **Зіставлення з ESP32** — якір MASTER (довгий спалах), далі ітеративна регресія `t_esp = a·t_cam + b` (зсув + дрейф).
4. **Субкадрове уточнення** — див. слайд 4.

## 4. Ключова ідея: менше за кадр (40 с)

- Спалах 70 мс, кадр 20 мс: на межі спалаху кадр засвічений **частково**. Частка яскравості f → де саме в
  межах експозиції почався спалах: `t = t_кадру + R·y + E·(1−f)`.
- R — rolling shutter (рядок y зчитується пізніше), E — експозиція; обидва підбираються з даних.
- **Нерегулярні повтори кадрів**: один дубль зсуває всі наступні кадри на −20 мс → сходинка в залишках; знаходимо й компенсуємо.
- **Візуал:** `results/run/.../subframe_ablation.png` або `errors_test.png` — «пилка» ±10 мс у B2 зникає в Ours.

## 5. Demo (50 с)

- `results/demo/<тейк>/demo.mp4` — сповільнено в 5 разів, навколо одного спалаху.
- Зверху: однаковий номер кадру — спалах на одній камері, решта «в іншому часі».
- Знизу: кадр, вибраний моделлю — спалах загоряється одночасно на всіх камерах (вставка зі збільшеним LED).

## 6. Results (50 с)

| Метод | RMS відносно ESP32 | розкид між камерами (RMS) |
|---|---|---|
| B0 — за номером кадру | 1570 мс | 3181 мс |
| B1 — зсув з MASTER | 35 мс | 32 мс |
| B2 — зсув + дрейф, до кадру | 11 мс | 32 мс |
| B2 + поправка на повтори | 5.9 мс | 16 мс |
| **Ours (субкадр + поправка)** | **2.3 мс** | **7.4 мс** |

- Кадр = 20 мс → Ours у ~3 рази менше за кадр між камерами; 95% спалахів у межах 4.1 мс від ESP32.
- 40 с спалахів на train досить, щоб модель трималась 2.7 мс на наступні 2.5 хв.
- Дрейф лише −4…+22 ppm: головні вороги — зсув старту, повтори кадрів і квантування кадром.
- **Слабкі місця:** один викид 26 мс (частково перекритий LED); R ≈ 0 на двох камерах — HDMI-карта,
  ймовірно, перетаймінговує рядки; потрібні LED у полі зору кожної камери.
- **Візуал:** `inter_camera.png` (лог-шкала, лінія «1 кадр»).

## 7. Conclusions (25 с)

- Синхронізація до кількох мс без genlock: два світлодіоди за $5 і лог ESP32.
- Результат — `sync_models.json` (a, b, E, R, повтори для кожної камери) → у Mocap Director / Captury.
- Далі: інтеграція в Mocap Director і перевірка в реальному часі під час запису; апаратний тригер / глобальний затвор як альтернатива.
